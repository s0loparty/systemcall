# LiveKit — Single Dokploy VPS

> Production target: one VPS managed by Dokploy.
> Dokploy owns the host-level Traefik and public ports 80/443.
> The project Docker Compose MUST NOT contain its own Traefik service.

## Signaling
Configure in Dokploy:
```text
livekit.example.com -> livekit:7880
```
HTTPS/WSS signaling passes through Dokploy-managed Traefik.

The Compose service uses `livekit/livekit-server:v1.13.4` and keeps signaling on internal port `7880`.

## Media
Media bypasses HTTP reverse proxy:
```text
7881/TCP
50000-60000/UDP
3478/UDP
```

Conceptual config:
```yaml
port: 7880
rtc:
  tcp_port: 7881
  port_range_start: 50000
  port_range_end: 60000
  use_external_ip: true
redis:
  address: redis:6379
```
Validate syntax against the pinned LiveKit version.

Implemented runtime config is generated by the Compose service from environment variables so Docker port publishing and LiveKit `rtc.port_range_start` / `rtc.port_range_end` cannot drift. API key/secret are injected at container startup from `LIVEKIT_API_KEY` and `LIVEKIT_API_SECRET`; no LiveKit secret is committed. `docker/livekit.yaml` remains a readable reference for the production shape.

## Local WSL2 / Docker Desktop
The production UDP media range is intentionally large. Docker Desktop on Windows/WSL2 can become unresponsive when publishing `50000-60000/UDP` locally. For local smoke checks, keep the same Compose file but override the range with a smaller value:

```bash
COMPOSE_PROJECT_NAME=livekit-smallcheck \
LIVEKIT_RTC_UDP_PORT_RANGE=50000-50020 \
LIVEKIT_API_KEY=devkey \
LIVEKIT_API_SECRET=devsecret \
DB_PASSWORD=secret \
APP_KEY=base64:AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA= \
REVERB_APP_ID=local \
REVERB_APP_KEY=localkey \
REVERB_APP_SECRET=localsecret \
VITE_REVERB_APP_KEY=localkey \
docker compose up -d redis livekit
```

Do not use the reduced UDP range for production.

## TURN
Initial connectivity strategy:
1. direct UDP WebRTC;
2. ICE/TCP on 7881;
3. TURN/UDP on 3478;
4. optional TURN/TLS on 5349 only after version/config verification.

Do not bind TURN/TLS to host 443 because Dokploy Traefik owns it.

Current Compose enables TURN/UDP on `3478/udp` and does not configure TURN/TLS.

If reliable TURN/TLS on public 443 becomes necessary, preferred upgrade is a dedicated LiveKit VPS/public IP.

## Tokens
Browser requests access from Laravel. Laravel validates room/member/password/ban/waiting room/target and signs the LiveKit token.

Never expose API secret.

Implemented token endpoint:
```text
POST /rooms/{public_id}/livekit-token
```

Implemented subroom switch token endpoint:
```text
POST /rooms/{public_id}/subroom-token
```

Current token service:
- uses `agence104/livekit-server-sdk`;
- reads `LIVEKIT_URL`, `LIVEKIT_API_KEY`, `LIVEKIT_API_SECRET` and optional `LIVEKIT_TOKEN_TTL` from Laravel config/environment;
- signs room-scoped tokens for LiveKit room `room-{public_id}` when no subroom target is selected;
- signs room-scoped tokens for `room_subrooms.livekit_room_name` when a target subroom is selected;
- uses `room_members.livekit_identity` as JWT identity;
- includes `room_subroom_id` and `room_subroom_public_id` in token metadata when the token targets a subroom;
- denies token issuance unless Laravel resolves an active room member from authenticated user or server-issued guest cookie;
- denies subroom switching when the target subroom does not belong to the room;
- denies banned participants;
- for waiting-room-enabled rooms, ordinary participants need an approved waiting-room entry before media token issuance; owner/moderator members may request tokens directly;
- maps RoomMember publish flags to LiveKit `canPublishSources`.

## Identity
Use backend-controlled RoomMember-based identity, e.g. `room-member:123`. Never use display name as security identity.

## Service layer
Centralize trusted LiveKit operations behind Laravel services:

- `LiveKitTokenService` signs room-scoped participant tokens.
- `LiveKitRoomService` removes participants and updates participant publish permissions for force-mute/mute-all.

Force-mute only revokes the microphone publish source. Remote unmute is intentionally not implemented.

## Frontend/media
Use LiveKit SDK for mic, camera, screen share, active speaker and media connection state. The current call page uses LiveKit local tracks for pre-join preview, publishes the selected microphone/camera after Laravel issues a token, and surfaces LiveKit media-device and reconnect events in the UI.

Subroom switching requests a fresh Laravel-authorized LiveKit token, disconnects from the current LiveKit room, and connects to the target LiveKit room. The frontend preserves the current microphone/camera enabled state across this reconnect. Screen sharing is not automatically resumed.

Current room options enable `adaptiveStream` and `dynacast`. Camera and screen-share publication request simulcast. Revisit selective subscriptions and publish presets when large-room limits are defined.

## Webhooks
Verify signatures and process idempotently. Webhooks are not frontend media realtime.

## Participant disconnect synchronization
Laravel membership cleanup now uses signed LiveKit webhooks as the authoritative fallback for abnormal client disconnects.

Webhook endpoint:
```text
POST /webhooks/livekit
Content-Type: application/webhook+json
Authorization: <LiveKit signed webhook JWT>
```

The endpoint validates the raw request body and authorization token with the PHP LiveKit `WebhookReceiver`. Invalid signatures are rejected with `401`.

The application reacts to `participant_left`. This covers cases where the browser cannot call the normal leave endpoint, including:

- tab/browser close;
- browser crash;
- device sleep/termination after LiveKit gives up reconnecting;
- prolonged network loss after LiveKit's reconnect window expires;
- mobile/process termination in the future React Native client.

A temporary network interruption does **not** immediately mark a participant as left. LiveKit first attempts reconnect/resume; membership is closed only when LiveKit emits the final `participant_left` event.

Every issued LiveKit token now rotates `room_members.media_session_id` and embeds that UUID in participant metadata together with `room_member_id`. Webhook cleanup requires all of the following to match the current Laravel state:

```text
room_member_id
livekit_identity
media_session_id
current LiveKit room name
```

This session guard is required because the same `RoomMember` identity is reused during reconnects, duplicate-tab replacement and subroom switches. A delayed `participant_left` from an older connection or previous subroom must not close a newer active membership.

Webhook handling is idempotent. Retried `participant_left` deliveries do not dispatch duplicate `RoomMemberLeft` application events after `left_at` is already set.

### Self-hosted LiveKit webhook config
The self-hosted LiveKit runtime config must include a webhook section whose signing key is one of the server's configured API keys:

```yaml
webhook:
  api_key: "${LIVEKIT_API_KEY}"
  urls:
    - "https://call.example.com/webhooks/livekit"
```

For the current Dokploy setup, replace `call.example.com` with the public Laravel application domain. The webhook URL must route to the `app` service through Dokploy Traefik; it is ordinary HTTPS application traffic, not a media port.

If `livekit.yaml` is generated by Compose at container startup, generate this `webhook` block there rather than maintaining a second divergent config file.
